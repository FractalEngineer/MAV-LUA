# v0.2.0 roadmap

## Goal

Make the ExpressLRS handset bridge a bounded, firmware-agnostic MAVLink transport. Firmware identification, parameter database selection, and firmware-specific wire behavior belong in MAV-LUA. Adding PX4 later must require no ExpressLRS bridge change.

v0.1.4 remains the supported ArduPilot implementation. This roadmap is deliberately deferred from that release.

## ExpressLRS transport boundary

- Keep one TX-side CRSF `0xAA` envelope and reuse the existing MAVLink uplink/downlink paths; do not change receivers.
- Authorize a small, explicit set of message IDs and command forms, but do not identify or interpret an autopilot family in the parameter session.
- Forward accepted payload bytes unchanged. Do not encode ArduPilot parameter-index or float conventions in bridge matching.
- Retain bounded packet/chunk sizes, subscription lifetime, request reservations, rate limits, link invalidation, and the fresh-heartbeat write gate.
- Keep ArduPilot readiness polling/conversion separate from the generic parameter transport. It may remain ArduPilot-specific without making parameter transport ArduPilot-specific.
- Add native tests using ArduPilot-shaped and PX4-shaped heartbeat, version, and parameter traffic. The PX4 fixtures must prove that targeting and raw parameter payloads cross the bridge without an ArduPilot dependency.

## MAV-LUA firmware adapters

- Add a small radio-side adapter interface for target discovery, firmware identity/version decoding, database selection, parameter reply correlation, and value/type conversion.
- Move the current ArduPilot component, `AUTOPILOT_VERSION`, `param_index=-1`, and float conversion rules behind the ArduPilot adapter.
- Keep the UI, database pager, edit/review flow, telemetry queue ownership, and verified-write state machine shared.
- Report unsupported firmware or versions explicitly before parameter traffic begins.
- Keep adapter modules lazy and bounded so Navigation and Messages remain compatible with older Lua firmware.

## PX4 path

1. Capture and fixture PX4 heartbeat, version, exact-name read, value, set, and readback traffic.
2. Implement the PX4 radio-side identity and parameter codec adapter.
3. Generate compact PX4 category/name databases from an official, pinned metadata source and document their provenance.
4. Add host tests for database selection, category paging, exact reads, type-safe edits, link loss, and verified saves.
5. Run the same sustained radio soak used for v0.1.3.

## Acceptance criteria

- Adding PX4 database and adapter support produces no diff in the ExpressLRS bridge.
- ExpressLRS native tests demonstrate firmware-neutral forwarding and preserve all request/write safety limits.
- MAV-LUA retains at most the visible database page, selected value, bounded decoder state, and bounded outstanding requests.
- Scrolling categories and names sends no MAVLink requests; only selecting a parameter reads its value.
- No write occurs during browsing or editing. Save still requires a fresh heartbeat, conflict reread, one set, and a separate matching readback.
- ArduPilot Plane/Copter behavior and legacy Navigation/Messages packages remain regression-tested.

## Out of scope until the transport boundary is proven

Descriptions, enum labels, bitmask editors, search, more vehicle families, and additional autopilot databases should not obscure the firmware-neutral transport work. They can follow once ArduPilot and PX4 use the same unchanged bridge.
