# v0.2.0 roadmap

## Status of the vehicle-discovered index: shelved

The on-radio parameter index was attempted twice and **failed on hardware both times**. The second
attempt got much further, then could not finish a build at about 739 names found. The radio has since
been measured directly, which is why the reason is known rather than guessed:

| Configuration | Used | Obtainable |
| --- | --- | --- |
| `bare` (no modules) | 13.4 KiB | 56 KiB |
| `build` (wire + index) | 38.2 KiB | **30 KiB** |
| `full` (all seven) | 58.6 KiB | 9 KiB |

A build's entire budget for staging tables, sort runs and file buffers is about **30 KiB**, the
binding limit is total size rather than fragmentation, and the application core cannot load inside a
Tools state at all. A lean rewrite that reduced resident staging by 26% on the host still did not fit,
which suggests the remaining cost is structural: the external merge sort exists only to produce one
globally alphabetical name file, and ordering by category-then-name instead would remove it.

**v0.1.3's packaged `.pdb` browsing is the browse source again and is what ships.** Any future
attempt should start from the measured budget above, prefer a design whose memory is O(page) rather
than O(list), and use `tools/diag/MAVHEAP.lua` to confirm the fit on the radio **before**
implementing it. The ExpressLRS list session any such design needs exists and is tested on
`feature/mavlink-lua-parameter-list`, but nothing consumes it.

## Goal

Make the ExpressLRS handset bridge a bounded, firmware-agnostic MAVLink transport. Firmware
identification, database selection, and firmware-specific wire behavior belong in MAV-LUA. Adding PX4
later must require no ExpressLRS bridge change.

This part of the roadmap does **not** depend on how parameter names are obtained, and it remains
valid and worth doing. v0.1.3 remains the supported ArduPilot implementation.

## ExpressLRS transport boundary

- Keep one TX-side CRSF `0xAA` envelope and reuse the existing MAVLink uplink/downlink paths; do not change receivers.
- Keep the envelope interception in `TXModuleEndpoint::handleRaw`, where the TX module claims the frame type exclusively before the router can read its chunk and length bytes as CRSF addresses. Do not move it back into the handset.
- Authorize a small, explicit set of message IDs and command forms, but do not identify or interpret an autopilot family in the parameter session.
- Forward accepted payload bytes unchanged. Do not encode ArduPilot parameter-index, float, or name-sorting conventions in bridge matching.
- Retain bounded packet/chunk sizes, subscription lifetime, request reservations, rate limits, link invalidation, and the fresh-disarmed write gate.
- Keep ArduPilot readiness polling/conversion separate from the generic parameter transport. It may remain ArduPilot-specific without making parameter transport ArduPilot-specific.
- Add native tests using ArduPilot-shaped and PX4-shaped heartbeat, version, and parameter traffic. The PX4 fixtures must prove that targeting and raw parameter payloads cross the bridge without an ArduPilot dependency.
- The bounded **list session** that a future index would need already exists here: it accepts `PARAM_REQUEST_LIST` and forwards streamed `PARAM_VALUE` without a per-index reservation while open, hard-capped by time and packet count, lease-gated, and mutually exclusive with normal reads. It passes its native tests, but no consumer uses it, so treat it as unproven.

## MAV-LUA firmware adapters

- Add a small radio-side adapter interface for target discovery, firmware identity/version decoding, index identity and rebuild decisions, parameter reply correlation, and value/type conversion.
- Move the current ArduPilot component, `AUTOPILOT_VERSION`, `param_index=-1`, and float conversion rules behind the ArduPilot adapter.
- Keep the UI, index pager, edit/review flow, telemetry queue ownership, and verified-write state machine shared.
- Report unsupported firmware or versions explicitly before parameter traffic begins.
- Keep adapter modules lazy and bounded so Navigation and Messages remain compatible with older Lua firmware.

## Vehicle-discovered index — shelved

Do not implement this without first measuring a design's fit on the radio. It was attempted twice
and failed both times; the second attempt reached about 739 names before running out of heap against
the measured 30 KiB budget. The steps below describe what was tried, and are kept so a future attempt
does not repeat them:

1. Add the bounded list session to the ExpressLRS bridge. **Done**, on `feature/mavlink-lua-parameter-list`; it passes its native tests but nothing consumes it.
2. Implement the on-device builder as the standalone Tools script `SCRIPTS/TOOLS/MAVLUA_BUILD_INDEX.lua`: capture the stream to a temporary file, sort it in bounded fixed-size runs, emit category records in one sequential pass, then rename atomically. **This is the step that does not fit.** The external merge sort exists only to produce one globally alphabetical name file, and that requirement is what makes peak memory scale with the vehicle rather than with a page. A future design should order by category-then-name instead and browse by filtered scan, which removes the sort and the merge entirely.
3. Reuse the existing fixed-record layout so the proven pager is unchanged, and report the index identity before parameter traffic. Still sound.
4. Make a never-indexed vehicle report clearly that it has no names yet, rather than an empty or stale tree. Still sound.
5. Run the same sustained radio soak used for v0.1.3, including rebuild after link loss mid-download. Not reached.

## PX4 path

1. Capture and fixture PX4 heartbeat, version, list-stream, exact-name read, value, set, and readback traffic.
2. Implement the PX4 radio-side identity and parameter codec adapter.
3. Add host tests for database selection, category paging, exact reads, type-safe edits, link loss, and verified saves.
4. Confirm the PX4 path needs no ExpressLRS bridge change, whichever browse source is used.

## Acceptance criteria

- Adding PX4 adapter support produces no diff in the ExpressLRS bridge.
- ExpressLRS native tests demonstrate firmware-neutral forwarding and preserve all request/write safety limits.
- The index build, if ever reintroduced, is bounded and atomic: a single temporary file plus bounded sort runs, no full-list retention, and no partial index left behind after a failure. **And it must first be measured to fit the radio's ~30 KiB build budget.**
- MAV-LUA retains at most the visible index page, selected value, bounded decoder state, and bounded outstanding requests.
- Scrolling categories and names sends no MAVLink requests; only selecting a parameter reads its value.
- No write occurs during browsing or editing. Save still requires a fresh disarmed state, conflict reread, one set, and a separate matching readback.
- ArduPilot Plane/Copter behavior and legacy Navigation/Messages packages remain regression-tested.

## Out of scope until the transport boundary is proven

Descriptions, enum labels, bitmask editors, search, more vehicle families, and additional autopilot adapters should not obscure the firmware-neutral transport work. They can follow once ArduPilot and PX4 use the same unchanged bridge.
