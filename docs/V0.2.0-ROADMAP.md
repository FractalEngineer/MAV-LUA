# v0.2.0 roadmap

## Goal

Replace packaged-database browsing with a vehicle-discovered parameter index, and make the ExpressLRS handset bridge a bounded, firmware-agnostic MAVLink transport. Firmware identification, index identity, and firmware-specific wire behavior belong in MAV-LUA. Adding PX4 later must require no ExpressLRS bridge change.

A parameter name is only usable once it has actually been read from the flight controller. There is no offline or pre-populated browsing, matching Mission Planner. v0.1.3 remains the supported ArduPilot implementation; its packaged databases are superseded as a browse source.

## ExpressLRS transport boundary

- Keep one TX-side CRSF `0xAA` envelope and reuse the existing MAVLink uplink/downlink paths; do not change receivers.
- Keep the envelope interception in `TXModuleEndpoint::handleRaw`, where the TX module claims the frame type exclusively before the router can read its chunk and length bytes as CRSF addresses. Do not move it back into the handset.
- Authorize a small, explicit set of message IDs and command forms, but do not identify or interpret an autopilot family in the parameter session.
- Add a bounded **list session** so the index can be built: accept `PARAM_REQUEST_LIST` and forward streamed `PARAM_VALUE` without a per-index reservation while the session is open. Hard-cap the session by time and packet count, keep it lease-gated, and make it mutually exclusive with normal reads so the one-reply-per-reservation guarantee is never weakened.
- Forward accepted payload bytes unchanged. Do not encode ArduPilot parameter-index, float, or name-sorting conventions in bridge matching.
- Retain bounded packet/chunk sizes, subscription lifetime, request reservations, rate limits, link invalidation, and the fresh-disarmed write gate.
- Keep ArduPilot readiness polling/conversion separate from the generic parameter transport. It may remain ArduPilot-specific without making parameter transport ArduPilot-specific.
- Add native tests using ArduPilot-shaped and PX4-shaped heartbeat, version, and parameter traffic. The PX4 fixtures must prove that targeting and raw parameter payloads cross the bridge without an ArduPilot dependency.

## MAV-LUA firmware adapters

- Add a small radio-side adapter interface for target discovery, firmware identity/version decoding, index identity and rebuild decisions, parameter reply correlation, and value/type conversion.
- Move the current ArduPilot component, `AUTOPILOT_VERSION`, `param_index=-1`, and float conversion rules behind the ArduPilot adapter.
- Keep the UI, index pager, edit/review flow, telemetry queue ownership, and verified-write state machine shared.
- Report unsupported firmware or versions explicitly before parameter traffic begins.
- Keep adapter modules lazy and bounded so Navigation and Messages remain compatible with older Lua firmware.

## Vehicle-discovered index

1. Add the bounded list session to the ExpressLRS bridge (above). Nothing else can proceed without it.
2. Implement the on-device builder as the standalone Tools script `SCRIPTS/TOOLS/MAVLUA_BUILD_INDEX.lua`: capture the stream to a temporary file, sort it in bounded fixed-size runs, emit category records in one sequential pass, then rename atomically. Never hold the whole list in memory and never write one record per received parameter. Keep it out of the Parameters page, which cannot afford the builder alongside the browser.
3. Reuse the existing fixed-record layout so the proven pager is unchanged, and report the index identity before parameter traffic.
4. Make a never-indexed vehicle report clearly that it has no names yet, rather than an empty or stale tree.
5. Run the same sustained radio soak used for v0.1.3, including rebuild after link loss mid-download.

## PX4 path

1. Capture and fixture PX4 heartbeat, version, list-stream, exact-name read, value, set, and readback traffic.
2. Implement the PX4 radio-side identity and parameter codec adapter.
3. Confirm the discovered index builds from a PX4 vehicle with no bridge change.
4. Add host tests for index build, category paging, exact reads, type-safe edits, link loss, and verified saves.

## Acceptance criteria

- Adding PX4 index and adapter support produces no diff in the ExpressLRS bridge.
- ExpressLRS native tests demonstrate firmware-neutral forwarding and preserve all request/write safety limits.
- No packaged or offline parameter names ship as a browse source; a name appears only after it was read from that vehicle.
- The index build is bounded and atomic: a single temporary file plus bounded sort runs, no full-list retention, and no partial index left behind after a failure.
- MAV-LUA retains at most the visible index page, selected value, bounded decoder state, and bounded outstanding requests.
- Scrolling categories and names sends no MAVLink requests; only selecting a parameter reads its value.
- No write occurs during browsing or editing. Save still requires a fresh disarmed state, conflict reread, one set, and a separate matching readback.
- ArduPilot Plane/Copter behavior and legacy Navigation/Messages packages remain regression-tested.

## Out of scope until the transport boundary is proven

Descriptions, enum labels, bitmask editors, search, more vehicle families, and additional autopilot adapters should not obscure the firmware-neutral transport work. They can follow once ArduPilot and PX4 use the same unchanged bridge.
